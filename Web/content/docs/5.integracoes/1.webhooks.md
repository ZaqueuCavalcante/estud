title: Webhooks

Um **webhook** é o caminho inverso de uma API: em vez de o seu sistema ficar perguntando ao Estud se algo mudou, o Estud avisa o seu sistema no momento em que a mudança acontece.

Na prática, você cadastra uma URL e escolhe quais **eventos** quer acompanhar. Sempre que um desses eventos ocorrer, o Estud envia uma requisição pra sua API com os dados do evento.

## Como configurar

O cadastro é feito em **Integrações**, no menu lateral.

1. Clique em **Criar webhook**
2. Dê um **nome** ao webhook, para você identificá-lo depois
3. Informe a **URL** que vai receber as chamadas
4. Marque os **eventos** que essa URL deve receber
5. Adicione **headers customizados** para **autenticação** das chamadas
6. Salve

A partir daí o webhook já está ativo. Você pode ter **vários webhooks**, cada um com sua própria URL e sua própria lista de eventos — e o mesmo evento pode ser enviado para mais de uma URL.

### Headers customizados

Os headers customizados são enviados em **todas** as chamadas daquele webhook, e é assim que o seu sistema confirma que a requisição veio mesmo do Estud. O uso mais comum é um **token de autenticação**, por exemplo:

| Chave | Valor |
|---|---|
| `Authorization` | `SEU_TOKEN_SECRETO` |

::warning
Use sempre uma URL `https` e valide o token no seu endpoint. Sem isso, qualquer um que descubra a sua URL consegue enviar dados falsos para ela.
::

## O formato das chamadas

Toda chamada é um `POST` com corpo JSON, no seguinte formato:

```json
{
  "event_id": "01K5F2G8QX7VN3ZC4M9TB6HDRY",
  "event_type": "StudentCreated",
  "occurred_at": "2026-09-05T13:22:10Z",
  "data": {
    "id": 123,
    "name": "João da Silva",
    "email": "joao.silva@email.com"
  }
}
```

| Campo | Descrição |
|---|---|
| `event_id` | Identificador único do evento |
| `event_type` | O tipo de evento que ocorreu |
| `occurred_at` | Data e hora do evento, em UTC |
| `data` | Os dados do evento — o conteúdo varia conforme o `event_type` |

O Estud considera a entrega bem-sucedida quando o seu sistema responde com qualquer status **2xx**. Qualquer outra resposta é registrada como erro.

## Eventos disponíveis

| Evento | Tipo | Quando ocorre |
|---|---|---|
| Aluno criado | `StudentCreated` | Um aluno é cadastrado na instituição |
| Professor criado | `TeacherCreated` | Um professor é cadastrado na instituição |
| Atividade publicada | `ClassActivityPublished` | Um professor publica uma atividade em uma turma |

### Aluno criado

Disparado sempre que um novo aluno é cadastrado na instituição.

```json
{
  "event_id": "01K5F2G8QX7VN3ZC4M9TB6HDRY",
  "event_type": "StudentCreated",
  "occurred_at": "2026-09-05T13:22:10Z",
  "data": {
    "id": 123,
    "name": "João da Silva",
    "email": "joao.silva@email.com"
  }
}
```

| Campo | Descrição |
|---|---|
| `id` | Id do aluno |
| `name` | Nome do aluno |
| `email` | E-mail cadastrado do aluno |

### Professor criado

Disparado sempre que um novo professor é cadastrado na instituição.

```json
{
  "event_id": "01M36YVSXER7XWRJCYZKKM0EFD",
  "event_type": "TeacherCreated",
  "occurred_at": "2026-09-07T13:22:10Z",
  "data": {
    "id": 456,
    "name": "Maria Oliveira",
    "email": "maria.oliveira@email.com"
  }
}
```

| Campo | Descrição |
|---|---|
| `id` | Id do professor |
| `name` | Nome do professor |
| `email` | E-mail cadastrado do professor |

### Atividade publicada

Disparado quando um professor cria uma atividade em uma de suas turmas — prova, trabalho, projeto ou apresentação.

```json
{
  "event_id": "01K5F2G8QX7VN3ZC4M9TB6HDRZ",
  "event_type": "ClassActivityPublished",
  "occurred_at": "2026-09-08T13:22:10Z",
  "data": {
    "id": 789,
    "class_id": 1011,
    "title": "Modelagem de Banco de Dados",
    "type": "Work",
    "due_date": "2026-09-12"
  }
}
```

| Campo | Descrição |
|---|---|
| `id` | Id da atividade |
| `class_id` | Id da turma onde a atividade foi publicada |
| `title` | Título da atividade |
| `type` | `Exam` (prova), `Project` (projeto), `Work` (trabalho) ou `Presentation` (apresentação) |
| `due_date` | Data limite de entrega, no formato `AAAA-MM-DD` |

## Idempotência

O campo `event_id` é o identificador único do evento, logo ele **não muda** se o evento for enviado de novo — por exemplo, num [reprocessamento manual](#reprocessamento-manual). Guarde esse valor do seu lado e ignore um `event_id` que você já processou — assim uma entrega repetida nunca vira um registro duplicado.

::note
Responda rápido e processe depois. O ideal é o seu endpoint apenas registrar o recebimento do evento, devolver 2xx e fazer o trabalho pesado de forma assíncrona depois.
::

## Quando a chamada falha

Toda chamada fica registrada em **Integrações > Chamadas**, com o evento, o status, o payload enviado e o histórico de tentativas. Ao abrir uma chamada você vê exatamente o que foi enviado, o código HTTP devolvido pelo seu sistema, o corpo da resposta e quanto tempo ela levou.

Uma chamada é marcada como **Erro** quando o seu sistema responde com um status fora da faixa 2xx, e também quando a requisição sequer chega ao destino — URL fora do ar, DNS inválido, certificado expirado ou timeout. Nesse último caso, a mensagem do erro de rede aparece no lugar da resposta.

::warning
Não há reenvio automático: uma chamada que falha permanece com status **Erro** até que alguém a reprocesse manualmente. Acompanhe a tela de **Chamadas** para identificar falhas.
::

Por isso vale a pena manter o endpoint tolerante: se ele ficar indisponível por alguns minutos, os eventos daquele intervalo só chegam depois de reprocessados.

### Reprocessamento manual

Depois de corrigir o problema do seu lado, abra a chamada com erro e clique em **Reprocessar**, na seção **Tentativas**. O Estud envia a chamada de novo e registra o resultado como uma nova tentativa — as anteriores continuam no histórico.

- O botão só aparece quando a chamada está com status **Erro**. Enquanto o reenvio não termina, ela fica como **Pendente**.
- O corpo enviado é exatamente o da chamada original, inclusive o mesmo `id` — então a deduplicação descrita em **Idempotência** continua funcionando.
- O reenvio usa a URL e os headers **atuais** do webhook. Se a falha foi uma URL errada ou um token vencido, edite o webhook antes de reprocessar.
- Uma chamada pode ser reprocessada quantas vezes for preciso, sempre que voltar a falhar.

::note
Só gestores com permissão para gerenciar webhooks conseguem reprocessar chamadas.
::
