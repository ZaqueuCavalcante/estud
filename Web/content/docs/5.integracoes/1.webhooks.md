title: Webhooks
description: Receba eventos do Estud em tempo real na sua própria API.
---

Um **webhook** é o caminho inverso de uma API: em vez de o seu sistema ficar perguntando ao Estud se algo mudou, o Estud avisa o seu sistema no momento em que a mudança acontece.

Na prática, você cadastra uma URL e escolhe quais eventos quer acompanhar. Sempre que um desses eventos ocorre, o Estud envia uma requisição `POST` com um JSON descrevendo o que aconteceu.

É assim que dá para manter o CRM sincronizado com as matrículas, disparar um e-mail próprio quando uma atividade é publicada ou alimentar um data warehouse — sem ninguém precisar exportar planilha nenhuma.

## Como configurar

O cadastro é feito em **Integrações**, no menu lateral.

1. Clique em **Criar webhook**
2. Dê um **nome** ao webhook — serve só para você identificá-lo depois
3. Informe a **URL** que vai receber as chamadas
4. Marque os **eventos** que essa URL deve receber
5. Se precisar, adicione **headers customizados**
6. Salve

A partir daí o webhook já está ativo. Você pode ter **vários webhooks**, cada um com sua própria URL e sua própria lista de eventos — e o mesmo evento pode ser enviado para mais de uma URL.

Para pausar um webhook sem perder a configuração, edite-o e desmarque **Ativo**. Webhooks inativos deixam de receber chamadas imediatamente.

### Headers customizados

Os headers customizados são enviados em **todas** as chamadas daquele webhook, e é assim que o seu sistema confirma que a requisição veio mesmo do Estud. O uso mais comum é um token secreto:

| Chave | Valor |
|---|---|
| `Estud-AuthToken` | `SEU_TOKEN_SECRETO` |

São aceitos até **20 headers** por webhook, com chave de até 100 caracteres e valor de até 1000.

::warning
Use sempre uma URL `https` e valide o token no seu endpoint. Sem isso, qualquer um que descubra o endereço consegue enviar dados falsos para ele.
::

## O formato das chamadas

Toda chamada é um `POST` com corpo JSON e a mesma estrutura, independente do evento:

```json
{
  "Id": "01K5F2G8QX7VN3ZC4M9TB6HDRY",
  "EventType": "StudentCreated",
  "OccurredAt": "2026-09-05T13:22:10Z",
  "Data": {
    "Name": "João da Silva",
    "Email": "joao.silva@email.com"
  }
}
```

| Campo | Descrição |
|---|---|
| `Id` | Identificador único desta chamada |
| `EventType` | O evento que ocorreu |
| `OccurredAt` | Data e hora do evento, em UTC |
| `Data` | Os dados do evento — o conteúdo varia conforme o `EventType` |

O Estud considera a entrega bem-sucedida quando o seu sistema responde com qualquer status **2xx**. Qualquer outra resposta é registrada como erro.

## Eventos disponíveis

| Evento | Tipo | Quando ocorre |
|---|---|---|
| Aluno criado | `StudentCreated` | Um aluno é cadastrado na instituição |
| Atividade publicada | `ClassActivityCreated` | Um professor cria uma atividade em uma turma |

### Aluno criado

Disparado sempre que um novo aluno é cadastrado na instituição.

```json
{
  "Id": "01K5F2G8QX7VN3ZC4M9TB6HDRY",
  "EventType": "StudentCreated",
  "OccurredAt": "2026-09-05T13:22:10Z",
  "Data": {
    "Name": "João da Silva",
    "Email": "joao.silva@email.com"
  }
}
```

| Campo | Descrição |
|---|---|
| `Name` | Nome do aluno |
| `Email` | E-mail cadastrado do aluno |

### Atividade publicada

Disparado quando um professor cria uma atividade em uma de suas turmas — prova, trabalho, projeto ou apresentação.

```json
{
  "Id": "01K5F2G8QX7VN3ZC4M9TB6HDRZ",
  "EventType": "ClassActivityCreated",
  "OccurredAt": "2026-09-05T13:22:10Z",
  "Data": {
    "Id": "01M0TWP3BDNVB6XSCJJZ6DZ595",
    "Title": "Modelagem de Banco de Dados",
    "Description": "Modele um banco de dados para um sistema de biblioteca.",
    "Type": "Work",
    "DueDate": "2026-09-12"
  }
}
```

| Campo | Descrição |
|---|---|
| `Id` | Id da atividade |
| `Title` | Título da atividade |
| `Description` | Enunciado da atividade |
| `Type` | `Exam` (prova), `Project` (projeto), `Work` (trabalho) ou `Presentation` (apresentação) |
| `DueDate` | Data limite de entrega, no formato `AAAA-MM-DD` |

## Idempotência

O campo `Id` é o identificador único daquela chamada, e ele **não muda** se a mesma chamada for enviada de novo. Guarde esse valor do seu lado e ignore um `Id` que você já processou — assim uma entrega repetida nunca vira um registro duplicado.

Quando o mesmo evento é enviado para **mais de um webhook**, cada um recebe um `Id` diferente: eles são chamadas distintas, e cada destino faz sua própria deduplicação.

::note
Responda rápido e processe depois. O ideal é o seu endpoint apenas registrar o recebimento, devolver `200` e fazer o trabalho pesado de forma assíncrona.
::

## Quando a chamada falha

Toda chamada fica registrada em **Integrações > Chamadas**, com o evento, o status, o payload enviado e o histórico de tentativas. Ao abrir uma chamada você vê exatamente o que foi enviado, o código HTTP devolvido pelo seu sistema, o corpo da resposta e quanto tempo ela levou.

Uma chamada é marcada como **Erro** quando o seu sistema responde com um status fora da faixa 2xx, e também quando a requisição sequer chega ao destino — URL fora do ar, DNS inválido, certificado expirado ou timeout. Nesse último caso, a mensagem do erro de rede aparece no lugar da resposta.

::warning
Não há reenvio automático: uma chamada que falha permanece com status **Erro** e não é tentada de novo. Acompanhe a tela de **Chamadas** para identificar falhas e, se necessário, buscar os dados pela API.
::

Por isso vale a pena manter o endpoint tolerante: se ele ficar indisponível por alguns minutos, os eventos daquele intervalo não chegam.
